# Раздел «Сообщения в ЛС» — спецификация

## Цель

Добавить локальный планировщик личных сообщений для небольшого списка из 1–3 заранее согласившихся контактов. Раздел не связан с keyword-триггерами, не запускается вместе с основным START/STOP и после установки всегда выключен.

## Ограничения

- От 1 до 3 контактов в одной задаче.
- Контакт вводится как `@username`, `username` или `https://t.me/username`; значения нормализуются в `username` без `@`.
- От 1 до 3 выбранных Telegram-аккаунтов с ролью «Бот-спамер».
- За один цикл каждый контакт получает не более одного сообщения.
- Аккаунты назначаются контактам round-robin и сохраняются в БД до отправки; один контакт не перебрасывается между аккаунтами после ошибки приватности.
- Одна общая текстовая строка сообщения на задачу.
- Повтор всегда конечный: от 1 до 12 запусков, по умолчанию 1.
- Допустимые интервалы: однократно, 5/10/30 минут, 1–12 часов, раз в сутки, раз в неделю.
- Пустое сообщение, более трёх контактов, более трёх аккаунтов, scout-аккаунт, дата в прошлом и бесконечный повтор отклоняются до сохранения.
- Созданная задача имеет состояние `paused`; отправка начинается только отдельной кнопкой START внутри раздела.
- Во время разработки и офлайн-тестирования никакие Telegram-процессы не запускаются.

## Почему отдельная очередь

Существующий `OutgoingMessageJob` рассчитан на ответы в каналах, требует канал и для обычного ЛС подменяет текст глобальным ответом. Новая очередь получает отдельные таблицы и use case, но повторно использует account leases, rate limiter, FloodWait/backoff и gotd-классификацию закрытых ЛС.

## Модель данных

### `scheduled_dm_tasks`

- `id`
- `message_text`
- `status`: `paused`, `active`, `completed`, `cancelled`, `error`
- `start_at`
- `interval_seconds` (`NULL` для однократной отправки)
- `max_runs` (1–12)
- `completed_runs`
- `next_run_at`
- `created_at`, `updated_at`

### `scheduled_dm_recipients`

- `task_id`
- `ordinal`
- `username`
- `peer_status`: `unchecked`, `resolved`, `open`, `closed`, `invalid`, `error`
- `last_error`
- `last_checked_at`

`resolved` означает только существование username. Telegram не предоставляет достоверную предварительную проверку возможности написать; `open` или `closed` устанавливается по результату реальной отправки.

### `scheduled_dm_accounts`

- `task_id`
- `ordinal`
- `account_id`

### `scheduled_dm_runs` и `scheduled_dm_deliveries`

Run фиксирует номер запуска и плановое время. Delivery фиксирует получателя, назначенный account ID, стабильный random ID Telegram, статус (`pending`, `sending`, `sent`, `closed`, `failed`), время попытки/завершения и безопасный код ошибки.

Создание run и deliveries выполняется одной транзакцией. Стабильный random ID снижает риск дубля при повторе после сбоя. Абсолютная exactly-once гарантия после принятого Telegram сообщения и аварии процесса невозможна, поэтому UI показывает фактический статус локального подтверждения.

## Сервисы

`ScheduledDMService` валидирует и сохраняет задачи, управляет START/STOP/отменой и возвращает безопасные DTO.

`ScheduledDMRunner` просыпается локально, берёт одну due-delivery через lease, проверяет назначенный аккаунт и вызывает отдельный `SendScheduledPrivateMessage`. Глобальные keyword-задания не создаются.

Username разрешается через `contacts.resolveUsername` от имени назначенного аккаунта непосредственно перед отправкой. `USER_PRIVACY_RESTRICTED`, blocked-user ошибки и подходящие `PEER_ID_INVALID` классифицируются как `closed` и не повторяются. FloodWait и временные сетевые ошибки используют существующий backoff, не увеличивая счётчик завершённых запусков до терминального результата каждой delivery.

После завершения всех recipients run помечается завершённым. Если `completed_runs < max_runs`, `next_run_at` вычисляется от предыдущего планового времени, чтобы перезапуск приложения не сдвигал расписание. Иначе задача получает `completed`.

## Wails API

- `ListScheduledDMTasks()`
- `SaveScheduledDMTask(draft)`
- `StartScheduledDMTask(id)`
- `StopScheduledDMTask(id)`
- `CancelScheduledDMTask(id)`
- `ResolveScheduledDMRecipients(id)` — проверяет существование username без отправки и не утверждает, что ЛС открыты.

API не возвращает пароль, session path, Telegram access hash или полный номер телефона.

## Интерфейс

Новый пункт бокового меню: **«Сообщения в ЛС»**.

Редактор содержит:

- textarea «Контакты» с 1–3 строками;
- выбор 1–3 подключённых spammer-аккаунтов;
- компактную таблицу `Контакт | Аккаунт | Статус ЛС | Последняя проверка`;
- поле «Сообщение»;
- дата и время первой отправки;
- выбор интервала;
- числовой ввод «Количество отправок» (1–12);
- кнопки «Сохранить», START, STOP и «Отменить».

До первой отправки показывается `Не проверено` или `Контакт найден`. После отправки: `ЛС открыты`, `ЛС закрыты`, `Ошибка`. Список задач и deliveries хранится локально и восстанавливается после перезапуска, но задачи не возобновляются автоматически после установки этой версии: пользователь должен нажать START.

## Тестирование

- Парсинг трёх форм username и отклонение ссылок не на Telegram.
- Лимиты контактов, аккаунтов и запусков.
- Долговечное round-robin назначение.
- Однократное и повторное расписание после перезапуска.
- Закрытая личка является терминальным результатом без смены аккаунта.
- FloodWait откладывает delivery.
- START/STOP изолирован от keyword automation.
- Wails DTO не содержит секретов.
- UI-тесты создания, паузы, возобновления, статусов и локального восстановления.
