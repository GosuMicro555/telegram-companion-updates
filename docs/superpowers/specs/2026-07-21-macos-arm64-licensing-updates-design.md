# Telegram Companion: macOS ARM64, лицензирование и обновления

Дата: 21 июля 2026 года

## 1. Цель

Подготовить Telegram Companion к продолжению разработки и распространению на Mac с процессором Apple Silicon. Первичный установщик передаётся пользователю лично, приложение активируется офлайн-лицензией для одного Mac, а последующие версии устанавливаются из приложения по модели HH Application Sender.

## 2. Границы

Поддерживается только `macOS arm64` на процессорах Apple M-серии. Минимальная целевая система — macOS 13. Intel Mac, Universal Binary, Mac App Store, Windows-версия основного приложения и онлайн-отзыв лицензий в эту работу не входят.

Ubuntu остаётся внутренней средой разработки и тестирования до окончательного переноса проекта. В дальнейшем основная разработка, финальная сборка, подпись, нотарификация и публикация выполняются локально на целевом Mac. Сборка на GitHub Actions может использоваться как дополнительная CI-проверка, но не является обязательной частью выпуска.

## 3. Варианты и выбранный подход

Рассматривались три варианта:

1. Sparkle 2, подписанный appcast и офлайн-лицензия. Это выбранный вариант: Sparkle берёт на себя безопасную замену `.app`, проверку обновления и перезапуск.
2. Собственный updater на Go с отдельным процессом-установщиком. Он даёт больше контроля, но повторяет сложную платформенную логику прав доступа, атомарной замены и восстановления после ошибки.
3. Ручная загрузка нового `.dmg`. Этот вариант проще, но не соответствует принятому пользовательскому сценарию HH Application Sender.

Sparkle используется только в публичной macOS-сборке. Внутренняя Ubuntu-сборка не проверяет публичные обновления и не требует активацию.

## 4. Каналы сборки

Единый исходный код поддерживает два неизменяемых при запуске канала:

- `internal`: существующая среда разработки без лицензирования и публичного updater;
- `public-macos-arm64`: распространяемое приложение с активацией и обновлениями.

Канал, версия, идентификатор приложения, URL appcast, публичный ключ лицензий и публичный ключ Sparkle задаются во время сборки. Их нельзя изменить настройкой интерфейса, переменной браузера или пользовательским файлом.

Публичная сборка использует стабильные идентификаторы и имя `Telegram Companion`. Dev-сборка на Mac получает отдельный идентификатор и отдельный каталог данных, чтобы тесты не могли повредить рабочие Telegram-сессии.

## 5. Каталоги и сохранность данных

Публичные пользовательские данные хранятся вне `.app` в стабильном каталоге:

`~/Library/Application Support/Telegram Companion/`

В нём остаются:

- локальная база данных;
- tdata и преобразованные MTProto-сессии;
- роли аккаунтов, каналы и статусы модерации;
- proxy-профили и настройки Tor/Snowflake;
- keyword, ответы и статистика;
- настройки интерфейса и отметка просмотра release notes;
- принятая лицензия.

Sparkle заменяет только приложение в `/Applications`. Обновление, переустановка и удаление `.app` не удаляют пользовательский каталог. Формат базы меняется только штатными миграциями приложения; перед миграцией продолжает работать существующая система резервного копирования.

## 6. Идентификатор Mac

Одна лицензия активирует один физический Mac. Публичное приложение получает `IOPlatformUUID` через нативный macOS-адаптер, нормализует его вместе с версией схемы и идентификатором продукта, затем вычисляет SHA-256.

Исходный UUID не показывается и не записывается в журналы. Пользователь видит только производный Machine ID. Переустановка приложения или macOS и замена системного диска не меняют Machine ID. Замена системной платы требует выпуска новой лицензии. Если получить устойчивый идентификатор невозможно, приложение показывает понятную ошибку и не создаёт случайную привязку.

## 7. Формат и проверка лицензии

Лицензии подписываются Ed25519. В публичное приложение встраивается только публичный ключ проверки. Закрытый ключ находится исключительно на Windows-компьютере владельца.

Подписанная нагрузка содержит:

- версию схемы;
- уникальный ID лицензии;
- продукт `telegram-companion`;
- разрешённый канал `public-macos-arm64`;
- Machine ID;
- имя владельца;
- необязательный комментарий;
- дату выпуска;
- необязательную дату окончания; по умолчанию лицензия бессрочная.

Канонически сериализованные данные и подпись доступны в двух равнозначных формах: текстовый ключ и файл `.tcomplicense`. Изменение любого поля делает подпись недействительной.

На каждом запуске проверяются структура, версия схемы, Ed25519-подпись, продукт, канал, Machine ID и срок действия. Принятая лицензия сохраняется в пользовательском каталоге и переживает обновления. Офлайн-схема не поддерживает удалённый отзыв лицензии; это осознанное ограничение первой версии.

## 8. Экран активации и запуск runtime

До успешной проверки лицензии публичное приложение показывает только экран активации:

- Machine ID и кнопку копирования;
- поле для текстового ключа;
- импорт `.tcomplicense`;
- кнопку активации;
- краткую ошибку на русском языке.

До активации не открывается рабочая база, не запускаются Tor/Snowflake, Telegram-клиенты, планировщики, сбор аналитики и отправка сообщений. После успешной активации основной runtime инициализируется один раз и открывается обычный интерфейс.

Поддерживаются отдельные сообщения для повреждённого ключа, неверной подписи, другого Mac, другого продукта или канала, неподдерживаемой схемы и истёкшего срока.

## 9. Генератор лицензий на Windows

На текущем Windows-компьютере создаётся отдельное внутреннее GUI-приложение `Telegram Companion License Generator.exe`. Оно не входит в `.dmg`, архив обновления или GitHub Releases.

Генератор предоставляет:

- ввод Machine ID;
- имя владельца и необязательный комментарий;
- необязательный срок действия, отключённый по умолчанию;
- выпуск подписанного текстового ключа;
- копирование ключа;
- экспорт `.tcomplicense`;
- локальную историю выпущенных лицензий без секретного ключа;
- экспорт и импорт зашифрованной резервной копии закрытого ключа.

Активный закрытый ключ защищается Windows DPAPI. Переносимая резервная копия шифруется паролем с использованием `scrypt` и аутентифицированного шифрования. Закрытый ключ, расшифрованные резервные копии и рабочие секреты исключаются из Git и сборочных артефактов.

Ключ лицензирования не используется для подписи приложения или обновлений. Потеря активного ключа и его резервной копии лишает возможности выпускать совместимые новые лицензии, но не отменяет уже выданные.

## 10. Поведение обновлений

Updater повторяет пользовательскую модель HH Application Sender:

1. После успешной активации и загрузки приложения ждёт две минуты.
2. Проверяет appcast по HTTPS.
3. Повторяет проверку каждый час, пока приложение запущено.
4. При отсутствии обновления или временной сетевой ошибке не мешает работе.
5. При наличии более новой публичной версии показывает кнопку `Обновить до версии ...`.
6. Загрузка начинается только после нажатия пользователя.
7. Та же кнопка показывает процент загрузки.
8. После проверки архива кнопка меняется на `Перезапустить и обновить`.
9. Sparkle заменяет `.app`, перезапускает приложение и сохраняет пользовательский каталог.
10. На первом запуске новой версии приложение один раз показывает русские release notes.

Состояния updater: `disabled`, `idle`, `checking`, `available`, `downloading`, `ready`, `error`. В состояниях `idle`, `checking` и восстанавливаемой ошибки кнопка не занимает постоянное место в интерфейсе. Ошибка проверки или загрузки не останавливает Telegram Companion; следующая периодическая проверка выполняется штатно.

Сравниваются только опубликованные версии канала `public-macos-arm64`. Внутренние версии не публикуются и не вызывают обновление.

## 11. Release-only репозиторий

Первоначальный нотарифицированный `.dmg` передаётся пользователю напрямую и не обязан размещаться в GitHub.

Отдельный публичный репозиторий GitHub не содержит исходный код Telegram Companion. Его постоянная ветка содержит только appcast, release notes и минимальное описание. В GitHub Releases размещаются:

- полный подписанный архив новой `.app` для резервного обновления;
- необязательные delta-архивы Sparkle для поддерживаемых предыдущих версий;
- подписи и контрольные данные;
- release notes.

Полный архив необходим, даже когда доступна delta: он используется для старых версий и при невозможности применить патч. Приложение не содержит GitHub-токен. Доступ к бинарному архиву публичен, но запуск приложения требует действующей офлайн-лицензии.

Порядок публикации атомарный: сначала загружаются и проверяются все release assets, затем последним обновляется appcast. Незавершённый выпуск не должен предлагаться пользователям.

## 12. Подпись и нотарификация

Финальный выпуск собирается на Mac с M-процессором с использованием актуальных Xcode Command Line Tools, Go, Node.js и Wails 2.

Процесс выпуска:

1. Собрать Wails-приложение как `darwin/arm64`.
2. Включить ARM64-версии Tor и Snowflake, ML-модель и остальные ресурсы.
3. Подписать все вложенные исполняемые файлы и framework изнутри наружу.
4. Подписать `.app` сертификатом Developer ID Application с Hardened Runtime и timestamp.
5. Создать архив обновления и первоначальный `.dmg`.
6. Отправить пакеты в Apple через `notarytool` и прикрепить билет нотарификации.
7. Подписать update-архив отдельным EdDSA-ключом Sparkle.
8. Сгенерировать appcast и delta-обновления.
9. Проверить Gatekeeper, подписи и запуск на чистом пользовательском профиле.
10. Опубликовать release assets и затем appcast.

Сертификат Developer ID и нотарификационные credentials хранятся в macOS Keychain. Закрытый ключ Sparkle также хранится только на машине выпуска или в защищённом CI secret. Ни один из них не совпадает с Windows-ключом лицензий.

## 13. Архитектурные компоненты

- `buildinfo`: типизированные параметры версии, канала и возможностей сборки.
- `license/domain`: канонический payload, кодирование и ошибки проверки без платформенных зависимостей.
- `license/machineid/darwin`: получение и хеширование Machine ID.
- `license/store`: хранение принятой лицензии вне `.app`.
- `license/runtime`: активационная граница перед инициализацией Telegram runtime.
- `updater/domain`: платформенно-независимая машина состояний для Wails UI.
- `updater/darwin`: мост к Sparkle 2 с событиями проверки, загрузки, прогресса и установки.
- `frontend/activation`: экран активации.
- `frontend/update`: компактная кнопка и прогресс обновления.
- `internal-tools/license-generator`: закрытый Windows-генератор лицензий.
- `scripts/release-macos-arm64`: воспроизводимая локальная сборка, подпись, нотарификация и подготовка appcast.

Интерфейсы лицензирования и updater не зависят от Telegram use cases. Существующая бизнес-логика начинает работу только после прохождения activation gate.

## 14. Ошибки и безопасность

- Сетевая недоступность GitHub считается нормальным временным состоянием.
- Неверная подпись appcast или архива блокирует установку и записывает безопасный код ошибки без URL с секретами.
- Прерванная загрузка не повреждает текущую `.app`.
- Ошибка установки оставляет предыдущую версию запускаемой.
- Логи не содержат исходный IOPlatformUUID, лицензионный ключ, закрытые ключи, tdata или proxy-пароли.
- Лицензирование препятствует обычному копированию, но не делает локально распространяемый бинарный файл невозможным для реверс-инжиниринга.
- Автообновление не включает START, Telegram-триггеры или отправку сообщений.

## 15. Проверка

Автоматические тесты покрывают:

- детерминированную нормализацию и хеширование Machine ID;
- Ed25519-подпись и проверку;
- повреждённую нагрузку, неверный Mac, канал, продукт, срок и схему;
- текстовый и файловый форматы лицензии;
- зашифрованную резервную копию ключа генератора и неверный пароль;
- границы `internal` и `public-macos-arm64`;
- переходы машины состояний updater;
- показ release notes один раз;
- отсутствие запуска Telegram runtime до активации.

Приёмка на реальном Mac M-серии включает:

- установку лично переданного нотарифицированного `.dmg`;
- прохождение Gatekeeper без ручного обхода защиты;
- отказ лицензии другого Mac и успешную активацию правильным ключом;
- сохранение лицензии после перезапуска;
- обновление тестовой публичной версии до следующей через GitHub Releases;
- сохранение базы, настроек, tdata и Telegram-сессий после обновления;
- единичный показ русских release notes;
- проверку подписи, нотарификации и архитектуры всех вложенных бинарных файлов;
- подтверждение, что обновление не запускает Telegram-автоматизацию.

## 16. Критерии готовности

Работа считается завершённой, когда:

1. основной проект продолжает собирать внутреннюю Ubuntu-версию без активации и updater;
2. Mac M-серии собирает подписанную и нотарифицированную публичную ARM64-версию;
3. публичное приложение не открывает основной runtime без корректной лицензии своего Mac;
4. закрытый Windows-генератор выпускает совместимые текстовые и файловые лицензии;
5. первоначальный `.dmg` можно передать человеку напрямую;
6. опубликованная тестовая версия обновляется до следующей через release-only GitHub;
7. обновление сохраняет все пользовательские данные;
8. исходники и закрытые ключи не входят в публичные артефакты;
9. Intel Mac и Universal Binary не создаются.
