# Интервальная очередь вступления в каналы — спецификация

## Цель

Не допускать одновременного вступления всех подключённых Telegram-аккаунтов в активируемый канал. Для каждого канала формируется долговечная последовательная очередь; все роли участвуют, но каждый аккаунт вызывает Telegram только после своего сохранённого времени.

## Настройки

В разделе «Каналы» рядом с формой добавления ссылок отображаются:

- `Интервал вступления от, минут`
- `Интервал вступления до, минут`

Допустимый диапазон каждого поля: 10–60 минут. Значения по умолчанию: 10 и 60. `from <= to`. Настройка сохраняется в `AppSettings` и применяется только к новым активациям; уже сформированное расписание не пересчитывается.

## Формирование очереди

После подтверждения включения канала `CatalogService.Toggle(..., active=true)` получает все eligible-аккаунты независимо от роли в стабильном порядке `created_at, id`.

- Первый аккаунт получает `join_not_before = now`.
- Для каждого следующего аккаунта генерируется новый интервал включительно между `from` и `to` минутами.
- Интервалы накапливаются: следующее время считается от предыдущего `join_not_before`, поэтому две заявки не планируются одновременно.
- Сформированные значения сохраняются вместе с membership intent в одной транзакционной операции хранилища.
- Повторный START, перезапуск приложения и периодический reconcile не меняют `join_not_before`.
- Повторная активация существующего активного канала не пересоздаёт очередь. После явного отключения и повторного включения новые значения назначаются только аккаунтам, которые ещё не являются участниками и не имеют pending-заявки.

Случайность используется только для распределения нагрузки, не влияет на обработку FloodWait и не скрывает ошибки. Источник случайности внедряется интерфейсом для детерминированных тестов.

## Хранение

В `account_channel_memberships` добавляется nullable `join_not_before`.

Существующие поля сохраняют значения:

- `status` остаётся `joining`, отдельный статус `scheduled` не вводится;
- `request_submitted_at` ставится только после `INVITE_REQUEST_SENT`;
- `joined_at` ставится после подтверждённого вступления;
- moderation history не очищается.

UPSERT хранит первоначальный `join_not_before`, пока membership не отключён/сброшен явной операцией. Миграция не назначает расписание существующим строкам: `NULL` означает «готово немедленно» для обратной совместимости.

## Выполнение

Перед любым join RPC `reconcileMembershipIntent` проверяет `join_not_before`:

- если время ещё не наступило, Telegram не вызывается, membership не меняется;
- если время наступило, выполняется существующая логика private/public invite;
- FloodWait и ошибки используют текущую обработку;
- pending moderation recheck не ограничивается `join_not_before`, потому что заявка уже подана;
- missing-intent автосоздание не может обходить очередь для активированного канала: оно загружает сохранённый intent или не выполняет join без него.

Все Telegram-клиенты и основной START/STOP остаются выключенными в ходе разработки. Добавление и активация каналов во время офлайн-проверки не выполняются.

## Отображение

В основной таблице каналов агрегированный статус остаётся совместимым. Для ещё не наступившей первой попытки показывается `Запланирован`, вычисляемый из `status=joining` и будущего `join_not_before`, без нового значения в БД.

В раскрытии по аккаунтам отображаются:

- аккаунт;
- роль;
- `Запланировано на`;
- текущий статус;
- дата заявки/вступления, если они уже существуют.

Раздел «Модерация каналов» продолжает включать только фактически отправленные заявки (`request_submitted_at != NULL`), поэтому ещё ожидающие своей очереди аккаунты не считаются заявками.

## Ошибки и атомарность

Активация канала и создание memberships выполняются атомарно на SQLite-уровне. При ошибке канал не остаётся активным с частичной очередью. Деактивация не удаляет moderation history; она только прекращает новые join RPC.

Постоянная ошибка ссылки остаётся на конкретном membership и не ускоряет последующие аккаунты. Изменение настроек интервала не затрагивает текущую очередь.

## Тестирование

- Детерминированная последовательность cumulative timestamps для 100 аккаунтов.
- Все роли включаются в очередь.
- Перезапуск/повторный reconcile не меняет времена.
- До `join_not_before` Telegram RPC не вызывается.
- В момент due вызывается ровно одна попытка.
- Pending recheck продолжает работать.
- Транзакционный rollback не оставляет частичную очередь.
- Настройки 10–60 валидируются и сохраняются.
- UI показывает поля, ошибки диапазона и вычисляемый статус `Запланирован`.
- Offline regression: moderation timestamps остаются неизменными.
